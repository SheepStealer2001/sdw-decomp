# Conventions and key facts

The facts every other note assumes, and the conventions the tables and tools follow.

## The target

- `SheepD3D.exe`, PAL PC release, SHA-1 `ca39374d53ae0030c5bd8c90dda45465e446dfe3`, 2,461,696 bytes. Built with Microsoft Visual C++ 6.0; image base 0x400000; not packed, no copy protection.
- Addresses are virtual addresses in hex (`0x40b060`).

## How it was built

- **Compiler:** Visual C++ 6.0 SP5 (CL 12.00.8804, C1 12.00.8867, C1XX 12.00.8964) with the **Processor Pack** back end (c2.dll 13.00.9044); static SP5 LIBCMT. Recipe: `/c /MT /Od /Gd /G6 /Ob1 /GX- /Zp8 /Op- /QIfdiv-`. Every switch is backed by a function that only it reproduces, except `/Ob1` against `/Ob2`, which is not uniquely recovered; `/Zp8` against `/Zp4` is told apart only by the layout of the `Timer` struct.
- **Not everything is `/Od`.** The DirectSound and video layer (`src/engine/sound.cpp`, `static_sound.cpp`, `stream_sound.cpp`, `wave_file.cpp`, `src/objects/video.cpp`, `video_player.cpp`) and the cinematic and stream player (`src/engine/cine*.cpp`, `stream_player.cpp`, `sfx_volume.cpp`) were built `/O2 /Oy-` (most with `/Ob2`); `src/engine/scenaric_loop.cpp` needs `/Ob2` and has part of its code (0x560182-0x5606d1) under `#pragma optimize("g")`; libjpeg was built `/O2 /Oy- /Ob2`. Each source file states its extra switches in a `match-flags:` line in its first 40 lines (`src/jpeg/vc6.json` for the unmodified IJG files).
- **Linker:** LINK 6.00.8447 with `/OPT:REF /OPT:ICF`, running on Microsoft's MSVCRT 6.0.8168 ([BUILDING.md §7](../BUILDING.md#7-linking-the-exe) says why that matters). The objects are linked in the order of `data/tu_map.json`.

## The address map

- Game and engine code lies below **0x565850**; from there on it is Microsoft's static C runtime.
- **libjpeg release 6** occupies `.text` 0x4222c0-0x42dae0, between the game's own objects (`src/jpeg/README-SDW.md`). Two caveats at its edges: `0x4222b0` (`xor eax,eax; ret`) is the game's `Video_NullFrameProc`, into which the linker folded libjpeg's identical `jpeg_mem_init`; and `0x42bc80`, a single `ret`, is libjpeg's `jpeg_mem_term`, which the game's own empty calls also land on. Identical bodies like these are link folding, not proof of where a range ends.
- DirectX SDK utility code (device enumeration and similar) is interleaved with the game code.

## Names

- Canonical names come from the game disc's headers (`Levels/Lvl-03/Scenaric_Classes.h`, `GameRes.h`) and from strings in the exe; they are preferred over invented ones. Functions are named `Module_Function` in the style of the original (`Flock_…`, `Load_…`, `SAM_STT_…`); C++ methods drop the class prefix (`ScnControllable::SteerRun`).
- **Three symbol tiers,** applied in this order, the first one that names an address wins:
  1. `data/symbols.csv` - curated by hand; new names go here.
  2. `data/symbols_modules.csv` - the names recorded while reading the code one module at a time. It is a frozen table: correct a name in it by adding a row to `data/symbols.csv`.
  3. `data/symbols_auto.csv` - generated by `tools/class_map.py` from the class registrations. The matcher, the Ghidra scripts, the header generators and the mod builder all give them that precedence.
- **A table row may not contradict matched source.** A declaration in a matched file compiles to the original's exact bytes; a row is prose. `tools/check_symbol_prototypes.py` checks the argument count of every row against the matched declarations.
- Every claim is marked *verified* (read in the machine code or the data bytes) or *inferred*. Do not promote a guess to a fact.

## Structs and enums

- `data/structs/<Struct>.csv`: one row per field, `offset,ctype,name,meaning,confidence`, offsets **absolute** within the object (a derived class lists its own fields; its bases come from `data/class_map.csv`, plain non-virtual ones from `data/class_bases.csv`). `confidence` is `verified` or `inferred`; the generated headers tag inferred fields `[inferred]`. A bitfield is a row typed `u8:1`, `u16:3`...; consecutive rows at one offset share a storage unit, first row = lowest bits.
- `data/enums/<Enum>.csv`: `value,name,meaning`; a first row starting with `#` describes the enum.
- Settle a disputed field from the actual `mov` / `movzx` / `movsx` in the listing. Ghidra prints `+ 8` when it has typed the pointer `undefined4 *`, which means byte offset 0x20.
- After any change: `python3 tools/structs_to_c.py`, then `cc -fsyntax-only -std=c11 work/layout_check.c` (every offset and size asserted); `python3 tools/vc6.py --all` compiles the headers with VC6 as well.

## Levels: two numberings

Players number the levels 0-14 plus two bonus levels, B1 and B2. On the disc, B1 sits after level 4 and B2 after level 8, which shifts everything after them:

| Player numbering | Disc folder |
|---|---|
| Level 0-4 | `Lvl-00` .. `Lvl-04` |
| **B1** | **`Lvl-05`** |
| Level 5-8 | `Lvl-06` .. `Lvl-09` |
| **B2** | **`Lvl-10`** |
| Level 9-14 | `Lvl-11` .. `Lvl-16` |

`Lvl-17` is Planet X, which has no player-facing number. The notes say which numbering a level number is in. `Levels/` also holds `Scene`, `Wheel`, `Intro`, `Fend`, `Ending` and `Demos` ([docs/01-executable-and-files.md](01-executable-and-files.md)).

**Axes.** Positions are three signed 16-bit values at object +0x0C / +0x0E / +0x10. The notes call them **x / y / z**: the vertical axis points **down** (more negative is higher).

## WAR level files

The resource table (at `g_pDav+0xc` in memory) is `u32[]` where the **top byte is the type and the low 24 bits a byte offset** into the blob at `g_pDav+0x10`; `g_pDav+0x14/+0x18` hold the `.MLT` string bank. `GetResourceType` 0x547470 classes them: 0 = types 3/4/0xB/0x26, 1 = type 5 (scenaric record), 2 = type 0xA (cinematic), 3 = types 8, 9, 0x27, 0x80-0x86 or any type with bit 0x40, 4 = ignored (types 1/2). `Install_WarResource` 0x5475cb publishes the type-3 ones: **0x80** collision grid, **0x81** collision triangles, **0x82** export table (`{u32 count; entries[]}`, relocated), **0x83** a three-u32 header (0x6ddf60/64/68), **0x84** the object/cluster grid (`ObjGrid_Init`), **0x85** `{u32 count; pair[2][]}` with the second word of each pair relocated against the blob base, **0x86** -> 0x585050.

Types 3, 4, 0xB and 0x26 are geometry records (`tools/war_meshes.py` reads them). With bit 0x40 set, 0x43 and 0x44 are the objects' static and animated models; animated models are stored at 8 times the level's units. Still undecoded as content: types 8, 9, 0xA and 0x27, and what 0x83's three words and 0x85's pairs mean. The level tools (`tools/war_*.py`) read these files directly.

## Ghidra

The scripts in `tools/ghidra/` load the tables into your own Ghidra project ([BUILDING.md §8](../BUILDING.md#8-ghidra-optional)). `ExportDecomp` writes `work/decomp/` atomically (it writes `decomp.tmp` and swaps), so never delete `work/decomp` beforehand. `ApplyClassTypes` builds structs from `work/struct_layout.tsv` rather than through Ghidra's C parser, whose alignment shifts the tails of large structs. The Ghidra project is disposable: the CSVs are the source of truth for names and types.
